# 插件与 Mod 开发者体验规范

本文从插件/Mod 开发者视角定义平台必须交付的产品能力。平台完成度不以“宿主能加载模块”为准，而以第三方开发者能否独立完成创建、调试、测试、打包、发布、升级和维护为准。

系统架构见 [38 插件与模块系统](features/38-pluginSystem.md)，阶段和 Host API 见 [插件与模块开发 API](pluginHookApi.md)，工程顺序见 [插件与模块系统实施计划](Plan/Plugin/PLUGIN-full-plan.md)。

Sprak Capture 采用开放可信 Mod 模型：启用后的插件可以使用全部公开阶段、动作和 Host API，不需要逐项申请权限。`capabilities` 可填写任意作者自定义标签，管理界面只原样展示；漏填、重复或新增标签都不会改变运行结果。宿主不施加调用超时、事件队列、并发上限、输出配额、存储配额或自动熔断。模块类型同样只表达职责，不限制它可以订阅哪些阶段。

## 1. 开发者角色

| 角色 | 典型目标 | 首选路径 |
|---|---|---|
| 规则作者 | 过滤、标注、拒绝、重定向或生成响应 | 声明式模块 / Wasm 模板 |
| 协议作者 | 解析私有协议、DNS、TCP/UDP 帧并贡献结构树 | Wasm `protocolDecoder` |
| Web 开发者 | 修改 HTTP、WebSocket，注册命令和检查器 UI | TypeScript sidecar / Wasm |
| 系统开发者 | 接入已有 C/C++/Rust 库，处理高吞吐字节流或直接改变宿主行为 | `native` / `nativeWorker` |
| 企业集成者 | 对接内部服务、导入导出格式、自动化审批 | sidecar / `backgroundService` |
| UI 作者 | 提供正文查看器、媒体渲染器、工作区面板或独立窗口 | 声明式 UI / WebView / Native UI |
| 维护者 | 发布、升级、迁移配置、诊断故障和兼容新宿主 | 包工具、兼容矩阵、诊断包 |

开发者不需要理解宿主内部 Rust crate、Tokio 任务、录制文件布局或前端私有状态。必须公开的概念只有 manifest、模块、阶段、动作、能力、配置、状态、贡献点和版本。

## 2. 必须闭合的开发旅程

```text
安装开发工具
  → 创建项目
  → 选择运行时和模块模板
  → 在模拟宿主中运行固定夹具
  → 连接本地开发宿主
  → 检查事件、动作、日志和预算
  → 热重载
  → 运行兼容与故障测试
  → 构建并校验包
  → 签名和发布
  → 监控、升级、迁移、回滚
```

每一步都必须有单条命令、结构化输出、稳定退出码和可复制诊断。开发者不应手写归档目录、计算摘要、修改用户数据目录或人工拼 RPC。

## 3. 开发工具 CLI

统一工具名为 `capture-plugin`。当前可直接执行的核心命令：

```text
capture-plugin new <目录> <插件ID> --runtime <wasm|sidecar|nativeWorker|native>
capture-plugin check <插件目录>
capture-plugin schema <输出目录>
capture-plugin fixture <夹具.json>
```

| 命令 | 开发者得到的结果 |
|---|---|
| `new` | 生成完整 manifest、配置 Schema、运行时入口、README 和可校验 TCP 阶段夹具 |
| `schema` | 从宿主权威 Rust 模型生成 manifest、事件、动作和夹具 JSON Schema |
| `check` | 校验 manifest、运行时入口、路径、配置 Schema 和贡献声明 |
| `fixture` | 校验夹具中的 manifest、订阅阶段、事件身份和动作边界 |

目录校验、宿主安装前校验和 CI 必须调用同一库实现。包构建、签名、发布、兼容矩阵、开发热重载和多语言代码生成继续作为同一 CLI 的扩展命令，不创建另一套工具或协议。

## 4. 项目脚手架

生成项目至少包含：

```text
example.protocol/
├─ plugin.json
├─ src/
├─ schemas/
├─ tests/
│  ├─ fixtures/
│  └─ integration/
├─ ui/
├─ README.md
├─ CHANGELOG.md
├─ LICENSE
└─ plugin.lock
```

官方模板覆盖：

1. Wasm HTTP 请求/响应改写。
2. Wasm 协议解码与事务标注。
3. TypeScript sidecar 命令和检查器贡献。
4. Native worker 高频 TCP/UDP 处理。
5. 正文查看器和流式媒体渲染器。
6. 导入器、导出器和后台集成服务。

模板必须包含正向、拒绝、超时、取消、停止、重载和升级测试，不能只给一个打印日志的空壳。

## 5. SDK 体验

官方 SDK 位于 [`Server/PluginSDK`](../Server/PluginSDK/README.md)，以宿主生成的 JSON Schema 和
[`PROTOCOL.md`](../Server/PluginSDK/PROTOCOL.md) 为唯一线上契约。C++、Rust、Go、Python 与 TypeScript
提供相同事件、动作和生命周期语义：作者注册普通函数，SDK 负责 ABI/JSONL、请求关联、字节所有权、
停止与销毁。C++/Rust 使用进程内 Native ABI；Python/TypeScript 使用 Sidecar JSONL；Go 可在 Native
与 Native Worker 之间按部署需求选择。每种语言目录都包含可构建示例和离线模拟测试，作者无需复制宿主
源码或手写 IPC。

每种官方 SDK 都必须提供：

- 强类型事件和动作构造器，禁止开发者手写字符串阶段名和补丁路径。
- 流式正文/数据报接口，默认不物化完整正文。
- 可取消调用、截止时间和背压状态。
- Host API 客户端、能力检查和可测试的 mock。
- 配置 Schema、秘密引用、私有状态和迁移助手。
- 命令、解码树、查看器和 UI 消息类型。
- 结构化错误、日志、指标和追踪上下文。
- API 弃用标记、版本协商与编译期兼容提示。

Rust、C/C++、TypeScript、Python SDK 的语义必须一致；语言差异只能体现在惯用写法，不能产生不同阶段、默认失败策略或正文边界。

### 5.1 有状态二进制 TCP 流插件

专门处理私有 TCP 协议的插件不是“对每个 socket read 回调改一次字节”。TCP 只提供有序字节流，单次读取可能包含半帧、一帧或多帧，因此模块必须使用 `streamTransformer` 并实现以下状态机：

```text
客户端字节块
  → clientToServer 独立缓冲
  → 找帧边界
  → 解密/验签
  → 结构化 DecodedFrame + 字段范围
  → 允许插件修改字段或负载
  → 重新序列化
  → 重算长度/校验和/MAC/认证标签
  → 输出零到多个完整帧

服务端字节块使用另一套完全独立的 serverToClient 缓冲和密码状态。
```

宿主已提供的 `StreamTransformerSession` 保证：

- 两个方向独立串行，双向可并发，避免共享半包缓冲污染。
- `NeedMore` 只保留受预算字节，不向线上发布半帧。
- 一个输入块可产生零个、一个或多个 `StreamOutputFrame`，输出允许比输入更长。
- 插件整个决定通过输出数量、单帧和总字节预算后才原子发布，失败不产生半截重封包。
- 每帧可同时贡献解码字段、标签和协议名，工作台展示结构树但线上只转发 `wireBytes`。
- TCP 半关闭时必须调用 `finish(direction)`；缓冲仍有残帧即返回错误，不能静默丢字节。
- 连接关闭通过 exactly-once `close()` 回收会话密钥、压缩字典和序列号状态。

插件自行承担的协议职责包括：帧头魔数、长度前缀、转义、压缩、序列号、重放窗口、密钥轮换、加密模式、填充、校验和、MAC/AEAD 标签和错误映射。秘密只通过宿主秘密引用取得，不写入 manifest、配置、夹具、调用追踪和录制事务。若协议在握手后才确定密钥或压缩参数，应把状态绑定到 `connectionId + direction`，不得使用全局变量串联不同连接。

被动 WinDivert SNIFF 数据只会以 `interceptionMode: observeOnly` 投递；这种输入允许解码与标注，不允许修改或重封包。只有真实代理接管的数据面可以返回 `Modify`、`Drop` 或 `Close`。

## 6. 阶段与行为发现

开发者门户和 IDE Schema 必须能回答：

- 当前阶段何时发生，输入是否仍可修改。
- 该阶段允许哪些动作和能力。
- 是否位于网络热路径，预算是多少。
- 输入是原始值、当前草稿还是最终值。
- 正文是否流式、是否可回放、能否请求完整体。
- 动作如何影响后续插件、线上流量和录制。
- 超时、崩溃、禁用、重载和服务停止时采用什么失败策略。

平台提供“阶段浏览器”：按协议和生命周期查看事件 Schema、示例输入、合法动作、Host API、性能等级和最小宿主版本。

## 7. 调试和热重载

开发模式必须提供：

- 独立开发实例，不污染正式启用版本和配置。
- 文件变更后构建新实例，健康检查成功再原子切换。
- 单次调用追踪：匹配理由、输入摘要、耗时、动作、输出大小和后续阶段。
- 按插件、模块、连接、事务、阶段和 `eventId` 过滤日志。
- 预算视图：队列、并发、CPU、内存、正文、输出、存储和句柄。
- 断点式事件暂停只作用于开发副本，不阻塞真实客户端；真实流量调试使用复制事件。
- 可导出脱敏复现包，在模拟宿主逐次执行并比较动作。

热重载不得直接覆盖正在运行的文件，也不得把旧实例的异步结果应用到新服务或录制代际。

## 8. 测试体系

### 8.1 单元和契约测试

- 阶段输入、动作输出和 Host API mock。
- manifest、配置 Schema、公开接口说明和依赖正反矩阵。
- 固定时钟、随机数、DNS、网络和秘密引用。
- 版本协商、弃用字段和未知字段。

### 8.2 流量集成测试

- HTTP/1.0、HTTP/1.1、HTTP/2、HTTPS、CONNECT、SSE 和 Range。
- WebSocket 分片、压缩、控制帧和关闭。
- TCP 半关闭、UDP 双向数据报、DNS UDP/TCP、IPv4/IPv6。
- 重复头、压缩正文、multipart、大正文、流媒体和客户端中止。
- 多插件顺序、短路、冲突、超时、队列满、崩溃和强制停止。

### 8.3 回归夹具

开发者可以从工作台选择事务或连接并导出脱敏夹具。夹具固定原始字节、阶段序列和预期动作；正文是否包含由导出者明确选择。

## 9. 配置、秘密和状态迁移

- 配置 Schema 自动生成设置页、校验、默认值、说明和 i18n 键。
- 秘密字段只返回“已配置”状态，SDK 使用短生命周期秘密引用。
- 配置更新先在开发实例验证，再原子发布新代际。
- 私有状态使用独立命名空间和事务 API；容量、格式、压缩和回收由插件作者决定。
- 每个版本声明配置/状态迁移器和可回滚边界。
- 迁移器可在独立副本或进程内运行；失败和回滚语义由作者在 manifest 中说明。
- 卸载时保留或删除状态由插件命令与用户操作共同决定，宿主不添加权限门禁。

## 10. 模块组合、顺序和冲突

开发者需要声明模块提供和消费的服务、阶段读写集合以及是否终止阶段。宿主在安装和排序时检测：

- 两个模块修改同一结构化字段。
- 多个模块同时声明合成响应或连接重定向。
- 解码器依赖不存在或产生循环。
- UI 命令、页签和快捷键 ID 冲突。
- 不兼容的完整正文需求和热路径预算。

冲突不靠“最后一个赢”的隐式规则。宿主显示执行计划和冲突原因，由用户选择顺序、禁用其中一项或使用模块声明的合并策略。

## 11. UI 与资源贡献

开发者必须能预览贡献点，而不必安装到正式配置：

- 设置表单及各语言文案。
- 命令面板、工具栏动作和事务上下文菜单。
- 检查器页签、解码树、正文查看器和媒体渲染器。
- 工作区面板、连接徽标和状态项。
- 图标、主题、键盘操作、无障碍名称和空/错/加载状态。

声明式贡献提供最佳跨版本兼容。作者也可以使用自定义 WebView、独立窗口或进程内 Native UI；直接依赖主窗口 DOM 或私有 CSS 时由作者自行适配宿主升级。

## 12. 打包、发布和供应链

开发者需要：

- 确定性构建和可复现包摘要。
- 发布者身份、签名轮换和吊销流程。
- 依赖锁文件、许可证清单和第三方公告生成。
- 行为说明变化、兼容范围、平台/架构和迁移说明。
- 预发布通道、分阶段发布、撤回和回滚。
- 商店页面、README、截图、图标、变更日志和支持链接校验。
- 包结构、路径和摘要一致性检查；运行行为与故障边界由插件作者自行测试。

本地开发包和生产包都可以由作者选择是否签名；来源与摘要只作为界面信息，不阻止加载。

## 13. 运行维护

发布后，开发者应看到：

- 安装量、启用量和宿主/API 版本分布的匿名聚合统计（用户可关闭）。
- 调用量、命中率、延迟分位数、运行时错误、崩溃和资源观测；宿主不会据此自动停用插件。
- 与插件版本关联的脱敏诊断包和可复现事件。
- 配置迁移成功率、更新失败率和回滚原因。
- 弃用 API 使用位置和最后支持版本。

遥测、外部上传和数据处理策略由插件作者实现并在说明中公开；宿主不拦截插件的网络或文件访问。

## 14. 文档体系

公开文档至少分为：

1. 五分钟入门。
2. 模块类型选择指南。
3. manifest 与能力参考。
4. 阶段和动作参考。
5. Host API 与 SDK 参考。
6. UI 贡献规范。
7. 测试、调试和性能指南。
8. 打包、签名、发布和审核指南。
9. 版本迁移和弃用指南。
10. 完整样例与常见故障索引。

所有示例由 CI 构建和执行；文档中的 manifest、命令和事件 JSON 必须参与自动验证。

## 15. 稳定覆盖与扩展准入

| 开发者需要 | 已发布契约 | 扩展该能力时的强制验收 |
|---|---|---|
| 创建项目 | 五种 SDK、可构建示例、`capture-plugin check/schema/fixture` | 模板、示例清单、入口文件和 Host 加载测试必须同时通过 |
| 获取强类型 API | C++、Rust、Go、Python、TypeScript 使用同一 Native ABI/Process JSONL | 新增字段必须同步五种 SDK、Schema、协议文档与边界测试 |
| 离线调试 | SDK 模拟器、真实 ABI/子进程契约测试和固定夹具 | 模拟输入输出必须与生产 Host 逐字段一致 |
| 热重载 | 包级 reload 与运行实例原子替换 | 旧实例停止、在途调用、配置迁移和失败回滚必须有并发测试 |
| 操作协议流 | Native/Sidecar/Worker 接入统一阶段内核；当前数据面覆盖 TCP、UDP 和连接关闭 | 新数据面阶段必须同时接入顺序、修改链、失败语义和真实流量测试 |
| 管理配置和状态 | 完整用户配置持久化、秘密引用和运行实例快照 | Schema 迁移、原子写入、重启恢复和损坏拒绝必须闭合 |
| 组合多个 Mod | 用户顺序、匹配覆盖、失败策略和执行痕迹 | 多插件顺序、短路、代际隔离和确定性重放必须通过 |
| 构建发布包 | 包安装、目录校验和入口检查 | 打包、签名、来源、依赖锁、撤回与回滚使用同一清单事实 |
| 诊断线上问题 | 实例并发、调用追踪、输入输出大小、动作和稳定错误码 | 新运行时不得吞掉作者 stderr、协议错误或生命周期失败 |
| 跨版本维护 | 插件清单、Native ABI、Process JSONL 与权威 Schema | 协议版本必须精确协商；不兼容版本在加载前拒绝 |

当前五种语言已经共享同一事件、动作和生命周期契约，Sidecar 与 Native Worker 可由生产 Host 直接加载。
扩展阶段时必须先更新权威 Schema、五种 SDK 类型与契约测试，再接入数据面；不得新增只有宿主内部
Rust 类型才能调用的私有 Hook。

## 16. 开发者视角的完成标准

- 新开发者在 10 分钟内复制任一官方示例、编写普通函数并由生产 Host 加载。
- 不阅读宿主源码即可完成 HTTP 改写、协议解码、检查器贡献和配置持久化。
- 本地模拟结果与真实宿主结果逐字段一致。
- 一条命令完成检查、测试、确定性打包和签名准备。
- 插件崩溃、超时、升级失败和配置迁移失败均能由开发者自行定位。
- 同一个包在声明支持的平台和宿主版本矩阵中自动验收。
- 发布者可以升级、撤回和回滚，用户配置与顺序不被静默覆盖。
- SDK、Schema、示例、文档和宿主 API 在同一提交和版本中发布。
