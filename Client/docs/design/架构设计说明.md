# Android 客户端架构

## 1. 边界

客户端只负责在 Native 中认证解封静态连接资料、经该节点下载云规则并执行数据面。连接资料
不进入界面、日志或持久缓存，应用范围与路由动作也没有本地编辑入口。客户端与服务端唯一共享定义位于
`Contracts/clientServerContract.md`。

模板只携带零长度 `assets/bootstrap/profile.bin` 和每 ABI 唯一的 Native 密钥槽，不能直接启动。
打包器为每个安装包生成同一份随机密钥写入两 ABI SO，再用独立 nonce 将节点、非空凭据和规则地址
封装为 XChaCha20-Poly1305 容器。Kotlin 只把资产字节交给 Native 解封，严格解析返回的可擦除二进制
明文后立即覆盖中间数组；旧 JSON/Base64 路径和进程级资料缓存均不存在。

## 2. 统一 Native 核心

`libroutesocks.so` 同时服务 VPN 与 Root，避免 Kotlin、透明代理和 TUN 各自实现一套规则：

- 解析并原子替换 `[DNS]`、`[RoutingRule]`、`[GRoutingRule]`、`[proxy_app]`。
- 按作用域执行 PORT、IP-CIDR、DOMAIN、DOMAIN-KEYWORD、FINAL 与
  PROXY、DIRECT、REJECT。
- 维护按作用域隔离的 DNS 地址到域名观察缓存，解析 HTTP Host 和 TLS ClientHello SNI。
- 提供 RFC 1928/1929 TCP CONNECT 与长期异步 UDP ASSOCIATE 转发。
- 把传统 DNS 53 改写到规则指定的主备服务器并直连；Native 内部解析也使用同一上游。
- 统一维护上传、下载、活动连接、接受和失败计数。

Native 入口固定分为两种上下文：

| 上下文 | 本地 SOCKS | Root TCP | Root DNS | 执行规则 |
| --- | ---: | ---: | ---: | --- |
| 其他应用 | 12580 | 12345 | 12346 | `[GRoutingRule]` |
| `[proxy_app]` 应用 | 12581 | 12347 | 12348 | `[RoutingRule]` |

两个上下文互斥，选中应用不会继承全局规则，其他应用也不会读取普通规则。
回环 SOCKS 端口虽只绑定 `127.0.0.1`，但 Android 其他 UID 仍可访问。每次数据面启动都使用
CSPRNG 生成不同于远端账号的内部 RFC 1929 凭据；Native 强制校验，HEV 初始化后立即
关闭只存在于当前进程匿名管道中的配置，不向 cache、files 或临时目录写入明文。

## 3. VPN 数据面

VPN 使用静态链接进 `libroutesocks.so` 的固定来源 `hev-socks5-tunnel` 构建 TUN/lwIP 数据面。修改点位于原始 TCP/UDP
五元组仍存在的会话创建位置：

1. 把协议、源地址/端口、目标地址/端口编码为固定 JNI 字节协议。
2. API 29 及以上在活动 `VpnService` 内调用
   `ConnectivityManager.getConnectionOwnerUid`。
3. UID 在 `[proxy_app]` 集合中选择 12581，否则选择 12580；归属失败直接拒绝该流。
4. 纯全局和纯选中应用规则使用固定上下文；API 26–28 遇到混合规则明确停止。

HEV 启动必须完成 Native 初始化握手后才发布 RUNNING。工作线程意外退出由运行期状态接口上报，
服务进入统一清理，不能只凭零统计伪报运行。

规则缓存把 ETag 和 UTF-8 正文放在同一个长度有界快照，先同步同目录临时文件，再用一次
`ATOMIC_MOVE` 提交。不再信任无代次标识的旧正文/ETag 分文件缓存。

## 4. Root 数据面

Root 服务通过 `su` 启动只加载 `libroutesocks.so` 的特权伴随进程，不复制或执行额外二进制。IPv4 使用
`iptables nat REDIRECT` 保留 UID 身份并把 TCP 与 UDP/53 送入对应透明入口：

- 选中 UID 的 TCP 与 UDP 分别进入 12347/12348。
- 其他 UID 的 TCP 与 UDP 分别进入 12345/12346。
- 客户端自身 UID 首条 RETURN，防止规则下载、上游 SOCKS 与指定 DNS 回环。
- 每次启动先清除所有重复旧 jump；停止删除完整链并验证无残留，同时兼容清理旧版本留下的 TPROXY 策略。

Android OUTPUT REDIRECT 返回的是改写后的回环地址，无法恢复普通 UDP 原目标。UDP 因此先进入两个独立
NFQUEUE，由伴随进程在 verdict 前保存源端点、真实目标和规则上下文，再放行给回环 REDIRECT 监听器。
映射缺失、过期或容量耗尽时直接 DROP，禁止把未知目标误发到本地端口；应用与伴随进程之间只使用匿名管道
传递配置和控制帧，不写入运行期秘密文件。

Android 设备常缺少 IPv6 nat；当前发布尚未启用 IPv6 透明数据路径。为避免 IPv6 绕过，Root 对
相同 UID 捕获范围安装置顶的 `ip6tables filter` TCP/UDP 拒绝规则；未被规则选中的应用不受影响。

## 5. DNS 与域名

规则必须声明唯一 PRIMARY，可选唯一 SECONDARY，且只能是 IP 字面量。TCP/UDP 53 请求保留
客户端事务语义，在主服务器失败时才使用备用服务器；不发送到 Sprak SOCKS，不使用系统 DNS。
DoT 853 被拒绝。DoH 是普通 HTTPS，数据面无法可靠区分，按 Host/SNI 的域名规则处理。

HTTP 嗅探只扫描完整请求头，TLS 嗅探支持分段及跨 record 的 ClientHello。缓存以
“作用域 + IP”作为键，避免选中应用和其他应用在共享 CDN 地址上相互污染。

目标自身携带域名时直接保留；数值目标优先使用同作用域最近一次 DNS 观察，并允许严格验证的
HTTP Host/TLS SNI 覆盖共享 IP 候选。只要得到域名，PROXY 路径就原样发送 SOCKS5 DOMAIN，
不会在客户端重新解析为 IP；只有 DIRECT 路径使用指定 DNS 做本地解析。因此服务端事务展示
的是应用可观察域名，而不是 HEV 中间层的数值目标。

标准 SOCKS 客户端在收到 CONNECT 成功前不会发送首包。为了让 VPN 数值目标在缓存缺失时仍能
执行域名规则，仅该路径先返回成功并有界收集首包；嗅探或后续建链失败表现为 EOF。域名目标、
缓存命中、无域名规则和 Root 透明入口均先完成实际建链再报告成功。

## 6. 生命周期

启动顺序为：认证解封密文资料 → 经 SOCKS 下载/验证规则 → 启动 Native → 安装 VPN 或 Root 入口 →
确认工作线程就绪 → 发布 RUNNING。停止顺序相反，并等待全部 TCP/UDP 工作线程退出。

模式切换先把当前模式推进到 STOPPED，关闭全部连接、TUN、iptables 链和 Native，再启动目标
模式。新模式到达 RUNNING 才向界面报告切换成功；FAILED 或超时均返回精确原因。
